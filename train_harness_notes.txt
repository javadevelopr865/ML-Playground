======================================================================
PART 1. REVIEW, FIXES, AMP/COMPILE, USAGE (2026-10-16)
======================================================================
This part summarises the review of the Trainer class in train_harness.py:
what was wrong or slow, what was changed and why, the new optional
arguments, and the DataLoader settings to use alongside it.

All changes were tested in a scratch Python environment (torch 2.14.1,
torchmetrics, macOS 26.6 on Apple Silicon). Tests covered CPU and MPS.
CUDA was not available, so CUDA behaviour is based on how PyTorch is
documented to work, not on a test run.


----------------------------------------------------------------------
1. BUGS FIXED
----------------------------------------------------------------------

1.1  OneCycleLR was stepped once per epoch instead of once per batch
     Problem: train_one_cycle() builds OneCycleLR with
       total steps = epochs * steps_per_epoch
     but the scheduler was only stepped at the end of each epoch. The
     schedule only got about 1/steps_per_epoch of the way through, so
     the learning rate stayed near max_lr/25 (4e-4 with the defaults)
     and never reached max_lr. Training converged much more slowly than
     it should have. This was the biggest cost in the file.
     Fix: train_one_cycle() sets an internal flag (_step_per_batch).
     While it is set, the scheduler steps after every optimizer step.
     Other schedulers (StepLR etc.) still step once per epoch. The flag
     is reset afterwards in a try/finally.
     Verified: OneCycle now completes all of its steps (e.g. 21/21) and
     the learning rate rises to max_lr and anneals back down.

1.2  Number of classes was taken from the number of samples
     Problem: for a dataset that wasn't a Subset, the code used
     len(dataset), which is the number of samples (e.g. 50000 for
     CIFAR-10), as num_classes. torchmetrics would either raise a shape
     error or build huge per-class state.
     Fix: num_classes comes from dataset.classes, unwrapping nested
     Subsets. There is also a new num_classes= argument for datasets
     without a .classes attribute. The task string is now lowercase
     ('binary' / 'multiclass'). (Since replaced: the task and class
     count now follow the model's output; see Part 3, section 4.)

1.3  A metric you passed in was not moved to the device
     Problem: `metric.device = device` does not move a torchmetrics
     metric. `device` is a read-only property, so the line would
     probably raise an error.
     Fix: self.metric = metric.to(device), for both custom and default
     metrics.


----------------------------------------------------------------------
2. PERFORMANCE FIXES
----------------------------------------------------------------------

2.1  loss.item() on every batch
     Problem: .item() forces the CPU to wait for the GPU on every step,
     so the GPU can't queue work ahead.
     Fix: the loss is summed on the device
       (total_loss += loss.detach())
     and read with .item() once per epoch.
     Side effect: GPU work is asynchronous, so the epoch timer would be
     slightly off. A _synchronize() helper (CUDA or MPS) runs before the
     timer stops.

2.2  Training metric received the non-detached output
     Fix: metric.update(y_pred.detach(), y), so the metric doesn't
     touch the autograd graph.

2.3  Host-to-device copies were blocking
     Fix: .to(device, non_blocking=True) in both training and
     evaluation. Transfers now go through a _to_device() helper.
     NOTE: this only helps if the DataLoader uses pin_memory=True on
     CUDA (see section 5).


----------------------------------------------------------------------
3. MINOR FIXES
----------------------------------------------------------------------

- Initializer.use_he_init now covers nn.Conv2d as well as nn.Linear.
  Before, conv layers kept PyTorch's default initialization. It also
  skips layers with bias=False instead of crashing.
- Removed the dead `def history(self)` method. The instance attribute
  self.history (a dict) replaced it as soon as __init__ ran.
  self.history is still available as before.
- The "best epoch" comparison now uses the metric's higher_is_better
  attribute (torchmetrics provides it), so lower-is-better metrics
  work. If the attribute is missing, higher is assumed better. The
  first epoch always counts as best (previously best_metric started at
  a hard-coded 0.0).
- The final checkpoint reload uses
    torch.load(path, map_location=self.device, weights_only=True)
  so a checkpoint loads onto the right device without unpickling
  arbitrary objects.

Behaviour changes to know about:
- self.device is now a torch.device, not a string.
- If you build a Trainer on a dataset without a .classes attribute and
  don't pass a metric, you now need to pass num_classes=. (No longer
  true: the class count is inferred from the model; see Part 3, section 4.)


----------------------------------------------------------------------
4. NEW FEATURES
----------------------------------------------------------------------

4.1  Mixed precision (AMP)
     What it does: runs the forward pass and loss in 16-bit floats
     (fp16 or bf16) where that is safe, keeping sensitive operations
     (e.g. the loss) in fp32. 16-bit math uses less memory bandwidth
     and faster hardware paths. Typical speedup is 1.5-3x for CNNs on
     NVIDIA GPUs; on MPS it is usually smaller and less predictable.

     How it is implemented (device-agnostic, no MPS-specific code):
       - torch.autocast(device_type=self.device.type, ...) around the
         forward pass and loss, in both training and evaluation.
       - torch.amp.GradScaler(self.device.type) for fp16. With bf16 or
         AMP off it is disabled and does nothing, so one code path
         covers every device.
       - The training step is:
           scaler.scale(loss).backward(); scaler.step(optimizer);
           scaler.update(); optimizer.zero_grad()

     Default precision per device:
       CUDA : bf16 if torch.cuda.is_bf16_supported() (Ampere or newer,
              no GradScaler needed), otherwise fp16 + GradScaler
       MPS  : fp16 + GradScaler. bf16 also worked on the tested
              setup, but older macOS/torch versions don't support it.
       CPU  : AMP off. bf16 autocast is often slower on CPUs without
              AMX/AVX512-BF16.

     Caveats:
       - With fp16, the GradScaler occasionally skips an optimizer step
         when it detects inf/NaN gradients, mostly early in training.
         The per-batch OneCycleLR step then gives a harmless
         "lr_scheduler.step() before optimizer.step()" warning.
       - If you add gradient clipping later, call
         scaler.unscale_(optimizer) before clip_grad_norm_.
       - Metrics receive fp16/bf16 logits. That's fine for accuracy
         (argmax); for probability-sensitive metrics pass
         y_pred.float().
       - On MPS, time a few epochs with amp=False and amp=True before
         relying on it. (Measured: fp16 AMP was ~30% slower for a small
         GRU model on mps; see Part 4, section 5.)

4.2  torch.compile
     What it does: a just-in-time compiler for the model. Instead of
     running each layer one operation at a time in Python, it captures
     the computation as a graph and generates optimized code for it.
     The first time the model runs:
       1. Capture (TorchDynamo): watches the Python code of forward()
          and records tensor operations into a graph. Code it can't
          handle (data-dependent ifs, print, numpy) causes a "graph
          break": that part runs in normal Python and the rest is split
          into separate graphs. It also records "guards" (input shape,
          dtype, device, model.training); if one fails later, it
          recompiles.
       2. Backward pass (AOTAutograd): works out the gradient
          computation ahead of time, so the backward pass is optimized
          too.
       3. Code generation (Inductor): Triton kernels on NVIDIA GPUs,
          C++ on CPU, Metal shaders on MPS. The result is cached and
          reused.

     Where the speedup comes from:
       - Fusion: e.g. BatchNorm -> ReLU -> add becomes one kernel that
         reads and writes memory once instead of three times. CNNs are
         often memory-bound, so this is the main gain. Convolutions
         themselves mostly still use cuDNN.
       - Less Python and kernel-launch overhead. mode='reduce-overhead'
         goes further and uses CUDA Graphs to replay a whole step with
         almost no CPU work (best for small models / small batches).
       - Autotuning: mode='max-autotune' benchmarks kernel variants
         and keeps the fastest. It compiles much more slowly.
       Typical result: about 1.2-2x faster for a CNN on a recent
       NVIDIA GPU, most when combined with AMP and channels_last.

     Benchmark on this Mac (small CNN, batch 64, time per training
     step):
       Device | Eager  | Compiled | First 5 steps compiled (incl. compiling)
       CPU    | 123 ms | 135 ms   | 10.8 s
       MPS    |  37 ms |  65 ms   |  2.3 s
     So compile made training SLOWER on both CPU and MPS here. Keep it
     off on the Mac; use it on NVIDIA GPUs.

     How it is implemented:
       - self.model stays uncompiled and the compiled version is stored
         as self._fwd. The forward pass uses self._fwd. This matters
         because a compiled module's state_dict keys get an
         '_orig_mod.' prefix; saving from it would give checkpoints
         that can't load into an uncompiled model. Checkpoints are
         saved from self.model, so keys stay plain (e.g. '0.weight').
       - The compiled wrapper shares the same parameters, so the
         optimizer and load_state_dict keep working on self.model.
       - model.train() and model.eval() produce different graphs
         (BatchNorm/dropout behave differently). Each compiles once and
         is then cached.
       - The first epoch after compiling is labelled
         "(incl. compile)" in the printed output so its slow time isn't
         mistaken for a problem.
       - A warning is raised if compile is on and the training
         DataLoader doesn't set drop_last=True (see section 5).
       - AMP's autocast and GradScaler work under compile, and the
         harness reads loss/y_pred straight away, which is safe even
         with CUDA Graphs.

4.3  channels_last memory layout
     What it does: stores image tensors as NHWC instead of NCHW. On
     NVIDIA GPUs this is the layout tensor-core convolution kernels
     prefer, especially with AMP and compile.
     How it is implemented: when on, the model is converted with
     model.to(memory_format=torch.channels_last) before the optimizer
     is created, and 4-D input batches are converted in _to_device().
     Checkpoints saved in channels_last load fine into a normal model.


----------------------------------------------------------------------
5. DATALOADER SETTINGS (set these where you build your loaders)
----------------------------------------------------------------------

These aren't in train_harness.py; set them where you create the
DataLoaders. For small CNNs, data loading is often the real bottleneck.

  pin_memory        = (device == 'cuda')
      Needed for non_blocking=True to speed up transfers on CUDA. Not
      supported on MPS: PyTorch warns and falls back to normal memory,
      so set it only for CUDA.
  num_workers       > 0   (e.g. 4-8, depending on CPU cores)
      Loads and augments batches in parallel worker processes.
  persistent_workers = True   (requires num_workers > 0)
      Keeps workers alive between epochs instead of restarting them.
  drop_last         = True   on the TRAINING loader when compile is on
      The smaller last batch otherwise triggers a recompile and can
      switch the graph to slower dynamic-shape code. The validation
      loader's last batch causes one extra compile, which is fine.

Example:
  train_dl = DataLoader(train_ds, batch_size=128, shuffle=True,
                        num_workers=4, persistent_workers=True,
                        pin_memory=(device == 'cuda'),
                        drop_last=True)
  valid_dl = DataLoader(valid_ds, batch_size=256,
                        num_workers=4, persistent_workers=True,
                        pin_memory=(device == 'cuda'))


----------------------------------------------------------------------
6. Trainer ARGUMENTS - NEW ONES AND RECOMMENDED VALUES
----------------------------------------------------------------------

  num_classes=None
      Leave as None if your dataset (or the dataset inside a Subset)
      has a .classes attribute. Otherwise pass the number of classes.
      Ignored if you pass your own metric.

  amp=True
      Mixed precision on CUDA and MPS (always off on CPU). Set False
      to compare speed or debug numerical issues.

  amp_dtype=None
      None picks automatically (see 4.1). Override with torch.float16
      or torch.bfloat16 if needed.

  compile=False
      False : no compilation (recommended on Mac CPU/MPS).
      True  : default compile mode (recommended on NVIDIA GPUs).
      'reduce-overhead' : CUDA Graphs; good for small models/batches.
      'max-autotune'    : slowest to compile, sometimes fastest.

  channels_last=False
      Set True on NVIDIA GPUs together with AMP and compile.

Recommended configurations:

  Mac (MPS):
    Trainer(model, train_dl, valid_dl, device='mps')
      # amp=True default (fp16); compile and channels_last off.
      # Time a few epochs with amp=False vs True.

  NVIDIA GPU:
    Trainer(model, train_dl, valid_dl, device='cuda',
            compile=True, channels_last=True)
      # amp=True default (bf16 on Ampere+); drop_last=True on train_dl.

  CPU:
    Trainer(model, train_dl, valid_dl, device='cpu')
      # AMP is off automatically; compile not recommended.

Training:
  trainer.train_one_cycle(n_epochs=..., max_lr=...)   # OneCycle, stepped per batch
  trainer.train(n_epochs=...)                         # any per-epoch scheduler
  trainer.evaluate(dataloader)
  trainer.history  # dict: train_loss, train_metric, valid_loss, valid_metric,
                   # learning_rate (+ per-output keys; see Part 3, section 7)

Initialization (now covers conv layers):
  model.apply(Initializer.use_he_init)

PART 2. KEEPING THE OPTIMIZER IN SYNC WITH THE MODEL (2026-10-17)
======================================================================
Status: APPLIED in commit a995d6a. Written 2026-10-17 as a plan; implemented as written:
Trainer.sync_optimizer(), called as the first line of train().

Problem
-------
Trainer.self.model is the same object the caller holds, so in-place changes are shared.
But the optimizer was built from the model's parameters at __init__ time. If layers or
parameters are swapped afterwards (e.g. model.fc = nn.Linear(...)), the optimizer keeps
updating the old, now-detached parameters and the new layer never trains.

Approach
--------
Patch the existing optimizer in place rather than building a new one:
  - the lr_scheduler and GradScaler hold references to self.optimizer, so a new optimizer
    would orphan the scheduler;
  - optimizer.state is keyed by Parameter objects, so state (Adam moments, step counts) for
    untouched parameters is kept automatically.

Rules:
  - parameters no longer in the model are removed from their group, and their state dropped;
  - new parameters are appended to param group 0 (NOT add_param_group(): schedulers record
    one base lr per group at construction, so a new group breaks an existing scheduler);
  - a parameter whose tensor was replaced with a different shape (p.data = ...) keeps its
    identity, so its stale state is reset to avoid a shape error on the next step;
  - a warning is emitted only when something changed, so the event isn't silent.

Implementation
--------------
Trainer.sync_optimizer() applies the rules above; train() calls it first. No other changes
were needed: the compiled _fwd wraps the same module (structural changes just trigger a
recompile), and train_one_cycle() goes through train().

Known limitations / decisions to revisit
----------------------------------------
- With multiple param groups (e.g. backbone vs head lrs), new params always land in group 0.
  If that matters, add a parameter such as sync_optimizer(group=0).
- If the caller built an optimizer over only trainable params (filtered on requires_grad),
  sync will add the frozen ones to group 0. Harmless (they have no grad, so steps skip them),
  but they will appear in the optimizer.
- A group whose params are all removed is left as an empty group (torch tolerates this), so
  scheduler group counts stay consistent.

Tested (scratchpad prototype)
-----------------------------
- Swapping the last Linear layer: warning reports 2 added / 2 removed; Adam state of
  untouched layers is unchanged; the new layer joins group 0 and gets state after training;
  an existing StepLR scheduler keeps working.
- Calling it again with no changes: no warning.
- Replacing a tensor via .data with a different shape: its state is reset; same shape: kept.

PART 3. TASK INFERENCE, CHECKPOINTING, BATCHES, INPUTS/OUTPUTS, DEVICES (2026-10-28)
======================================================================
Status: APPLIED 2026-10-28. Sections 0-6 are in commit c11bab5; section 7 (multiple inputs and
outputs) and the docstrings are in the commit that follows it; section 8 (device placement) in
the one after that.
Started from a failing learner.train() in ageron/Ch14.ipynb (cell 137: IMDB sentiment
analysis with frozen BERT embeddings + bidirectional GRU). All changes below were tested
against small synthetic models/dataloaders in ~/.venv (torch 2.14.0, torchmetrics 1.9.0).


0. The original error, and why the traceback was misleading
------------------------------------------------------------
    AttributeError: 'list' object has no attribute 'to'

Cause: the notebook's collate_fn returned the labels as a plain Python list
([[label] for review in batch]). Trainer._to_device called y.to(device) on it.
(X was a transformers BatchEncoding, which has its own .to(), so X was fine.)

The traceback pointed at _temporary_lr_schedule and at the `elif self.device.type == 'mps'`
line, neither of which can raise this. ageron/harness.py is a symlink to train_harness.py,
and the file had been edited after the kernel imported it: IPython shows the *old* line
numbers next to the *current* file's text. The real frames were train() -> _to_device().
Lesson: after editing the harness, restart the kernel or importlib.reload(harness) before
trusting a traceback.


1. Dataloaders assigned before task inference (your change)
------------------------------------------------------------
__init__ called _get_task() -- which reads self.train_dataloader -- before
self.train_dataloader was assigned. The assignments now come first.


2. Inferred num_classes reaches the metric (your change)
---------------------------------------------------------
_get_task() now returns (task, num_classes) so the default
torchmetrics.Accuracy(task=..., num_classes=...) gets the inferred count. Before, it got
the original argument (None), which breaks multiclass Accuracy.


3. Metric target cast: _metric_target()
---------------------------------------
BCEWithLogitsLoss needs float targets; torchmetrics classification metrics are documented
to expect int targets. So the same y may need two dtypes. The harness now casts float
targets to long, for the metric only, when the metric is a torchmetrics classification
metric (detected via the metric class's module). Regression metrics are untouched.

Note: torchmetrics 1.9 turned out to accept float 0./1. targets for binary Accuracy, so
this is currently a safety net rather than a required fix. It's the one place the harness
deliberately converts types, because no single correct target dtype satisfies both the
loss and the metric.


4. Task inference rewritten: _get_task()
----------------------------------------
Old rule: binary if num_classes <= 2, where num_classes came from dataset.classes or from
the model output via `_l[1] if len(_l) > 2 else _l[-1]`. Two bugs:
  - 2-class models with 2 logits (CrossEntropyLoss) were labelled binary and got
    BCEWithLogitsLoss -> "Target size ([16]) must be the same as input size ([16, 2])".
  - Models returning shape (B,) used _l[-1] = the batch size as num_classes -> multiclass
    with 16 classes; training ran silently with loss ~23 and accuracy 0.

New rule: the task follows from the model's output, not the class count.
  - Probe one batch through the model under torch.no_grad() in eval mode (so BatchNorm
    running stats aren't updated), then restore the previous train/eval mode.
  - 1 logit per sample ((B,) or (B, 1)) -> binary (BCEWithLogitsLoss, BinaryAccuracy).
  - C logits along dim 1 ((B, C) or (B, C, L)) -> multiclass with num_classes = C,
    even when C == 2.
  - If num_classes (passed in, or from dataset.classes) disagrees with C, warn and use C.
Cost: one extra forward pass at Trainer construction, but only when criterion or metric
isn't passed.


5. checkpoint_path=None now disables checkpointing
--------------------------------------------------
`checkpoint_path or f'{token}.pt'` meant None still produced a random file name, so the
`if self.checkpoint_path is not None` guards never fired and every Trainer wrote a new .pt
file into the working directory.
  - default is now checkpoint_path='auto' -> random file name (old default behaviour)
  - None -> no saving, and no reload of the best weights at the end of train()
  - a string -> that path, as before
Anything that passed None explicitly now gets no checkpoints.


6. Batch handling: recursive device move, prepare_batch hook, clear errors
--------------------------------------------------------------------------
Design decision: be flexible about the *structure* of a batch, strict about the *types*
inside it. The harness should not convert a list of labels to a tensor on its own because:
  - it can't know the right dtype: torch.tensor([[0], [1]]) is long, which is right for
    CrossEntropyLoss and wrong for BCEWithLogitsLoss -- auto-conversion just turns a clear
    error into a confusing one inside the loss;
  - conversion belongs in the DataLoader: collate_fn runs in worker processes, and
    pin_memory (which makes non_blocking=True transfers overlap compute) only pins tensors;
  - default_collate already returns tensors, so a list showing up usually means a bug in a
    custom collate_fn.

What was implemented:

_move(obj, channels_last=False)
    Moves a nested batch to the device: tensors via .to(device, non_blocking=True);
    objects with their own .to() (e.g. BatchEncoding) via that; dicts/Mappings, lists,
    tuples and namedtuples recursively; anything else (strings, ids kept for debugging)
    passes through unchanged. channels_last applies to 4-D tensors anywhere in the
    inputs, never to targets.

prepare_batch=None   (new Trainer argument)
    prepare_batch(batch) -> (X, y), called on every raw batch before the checks and the
    device move (so it runs on CPU). For deliberate conversions, e.g.
        prepare_batch=lambda b: (b[0], torch.tensor(b[1], dtype=torch.float32))
    or for splitting Hugging Face-style dict batches:
        prepare_batch=lambda b: ({k: v for k, v in b.items() if k != 'label'}, b['label'])
    The train/evaluate loops now iterate whole batches (`for batch in loader`) so a batch
    no longer has to unpack as (X, y) before the hook runs.

_to_device(batch)   (signature changed: was _to_device(X, y))
    Runs prepare_batch, checks the batch, then moves it. Raises TypeError when:
      - the batch isn't an (inputs, targets) pair -- message shows what arrived and an
        example prepare_batch that splits a dict batch;
      - inputs or targets contain no tensors at all -- message shows the value and, for
        targets, which dtype each common loss needs. The original IMDB bug now reads:
          TypeError: batch targets contain no tensors: got list [[0], [1], [0], ...].
          Return tensors from your dataset/collate_fn (e.g. torch.tensor(labels,
          dtype=torch.float32) for BCEWithLogitsLoss, dtype=torch.long for
          CrossEntropyLoss), or pass prepare_batch=... to Trainer to convert them.

Limits:
  - The check only rejects parts with *no* tensors. A dict with one tensor plus a stray
    list of ints passes and fails later in the model or loss.
  - A custom loss that takes targets with no tensors at all would be rejected; add an
    opt-out if that's ever needed.
  - Code outside the harness calling _to_device(X, y) must switch to _to_device((X, y)).


7. Multiple inputs and multiple outputs
---------------------------------------
Multiple inputs
    The recursive mover (section 6) already moved nested inputs; what was missing was the call.
    New rule, in _forward(): a plain tuple of inputs is unpacked, model(*X); everything else
    (tensor, dict, list, namedtuple, BatchEncoding) is passed as one argument, model(X).
    Dicts are deliberately NOT unpacked into keyword arguments: models like the Ch14 IMDB model
    take the whole encoding as one argument. For a model that wants keywords (e.g. a Hugging
    Face model), wrap it or have prepare_batch return a tuple.
    A dataset yielding (x1, x2, y) still needs prepare_batch=lambda b: (tuple(b[:-1]), b[-1]);
    the "expected an (inputs, targets) pair" error now suggests exactly that.

Multiple outputs
    The model may return a tuple/list (outputs named 0, 1, ...), a namedtuple (named by field)
    or a dict (named by key). Targets use the same structure; a single target tensor is shared
    by every output (the usual case for auxiliary classifiers).

    criterion   one loss applied to every output, or a list/dict with one per output.
                Must be given explicitly for multi-output models (no inference).
                Limitation: a single loss is always applied per output, so a joint loss that
                needs all outputs at once (e.g. contrastive between heads) isn't supported.
    metric      one metric (deep-copied per output, so their states don't mix), or a
                list/dict with one per output; None = no metric for that output. With
                metric=None the model gets no metrics and monitor stays on the loss.
    loss_weights  Trainer(loss_weights=...) as a list/dict; outputs not listed get 1.0. The total
                loss is sum(weight * loss) -- a sum, not a mean, so adding heads doesn't
                silently shrink the gradients (same as Keras). Weight 0 skips that output's loss
                (its metric is still tracked if it has a target).
                train(loss_weights=...) and train_one_cycle(loss_weights=...) override them
                for this and later runs -- the same pattern as train(lr=...). Weights live on
                the Trainer because they define the objective that validation and checkpointing
                use; the override covers changing them between training phases.
    monitor     what picks the best checkpoint and drives early stopping:
                  'loss'           the weighted validation loss (lower is better)
                  'metric'         the metric of a single-output model
                  <output name>    that output's metric (direction from higher_is_better)
                Default: 'loss' for multi-output models; for single-output models it stays
                'metric', so existing notebooks checkpoint exactly as before.
    targets     None for an output skips its loss and metric for that batch. A target missing
                from the dict/tuple is an error unless that output's weight is 0.

    Models that return auxiliary outputs only in train mode (GoogLeNet/Inception): in eval
    mode, a lone tensor output is treated as the first output. The output structure is always
    taken from a train-mode forward pass -- during training, or, if evaluate() is called first,
    from a probe batch in train mode under no_grad with all buffers (BatchNorm running stats)
    restored afterwards.

    Per-output settings are checked against the output names on the first forward pass, with
    clear errors: entries for outputs that don't exist, outputs without a criterion, monitor on
    an output without a metric, a missing criterion for a multi-output model, and so on.

History, printout, evaluate()
    self.history now starts empty and fills in on the first epoch (it used to start with fixed
    keys). Single-output keys: train_loss, train_metric, valid_loss (new), valid_metric,
    learning_rate. Multi-output adds e.g. train_loss/aux, valid_loss/aux,
    train_metric/main, valid_metric/main.
    The per-epoch line now also shows valid loss, and '(best)' marks the monitored value.
    Per-output losses go to history only, to keep the line short.
    evaluate(dl): single output -> the metric value (a float now; it used to be a 0-d tensor);
    multi-output -> a dict of 'loss', 'loss/<name>', 'metric/<name>'.

Internal restructuring
    - train() and _evaluate() share one _run_epoch(); batches are counted, so the averages no
      longer use len(dataloader).
    - The probe forward pass at construction (only when criterion or metric is missing) feeds
      _get_task(out_shape, num_classes), which is now a pure function; the cached _task is gone.
    - _metric_target(metric, y) checks each metric separately.

8. Device placement: device='auto' / 'model', models spread over devices
-------------------------------------------------------------------------
Problem: with device not given, a model on the cpu was silently moved to mps/cuda. Moving a
model to the cpu on purpose (e.g. to work around the Ch14 "scaled_dot_product_attention for
MPS does not support dropout" error) therefore had no effect, and nothing said why.

Intent can't be detected: a freshly built model and one moved with .to('cpu') are identical
(.to('cpu') on a cpu model is a no-op and PyTorch records no history of .to() calls). The one
real signal is a model spread over several devices -- nobody does that by accident.

So instead of guessing, the move is made visible and can be switched off:
  device='auto'   (default; None means the same) a model on an accelerator stays where it is;
                  a cpu model is moved to cuda/mps when available, with a warning:
                    Trainer moved the model from cpu to mps; pass device='cpu' to train on the
                    cpu, or device='model' to always keep the model where it is.
  device='model'  always keep the model where it is.
  'cpu', 'mps', torch.device(...)   used exactly as given (no warning).

Why 'auto' stays the default rather than 'model': keeping the model in place is more
predictable, but fails silently the other way -- forget .to(device) once and a BERT model
trains on the cpu at a fraction of the speed. The warning gives most of the predictability
without breaking notebooks that rely on the automatic move.

Models spread over several devices (parameters and buffers on more than one device):
  - 'auto' and 'model' never move them; inputs go to the device of the first parameter.
  - an explicit single device raises a ValueError instead of collapsing the model onto it.
  - targets are moved to the device of the output they belong to before the loss, and outputs
    and targets are moved to the trainer's device for the metrics (_align()).
  - mixed precision is turned off, with a warning, when the devices are of different types
    (e.g. mps + cpu): torch.autocast covers one device type, so the cpu half got fp16 inputs
    from the mps half and failed with "mat1 and mat2 must have the same dtype".

Tested on mps: every placement combination above (cpu/mps models x default/None/'cpu'/
torch.device/'model'/'mps'), a model split over mps and cpu trained end to end, and all the
earlier test suites on cpu and mps.


Known, deliberately left as is
------------------------------
sync_optimizer() adds every model parameter missing from the optimizer, including frozen
ones you deliberately left out. Harmless while they stay frozen (no grads), useful if you
unfreeze later, but they always land in param_groups[0], which matters with per-group
learning rates.

3. verbose=True   (new Trainer argument)
-----------------------------------------
verbose=False turns off everything above, the per-epoch lines and the progress bars, e.g.
for hyperparameter sweeps. Warnings are still shown. Can be changed later: trainer.verbose.

4. Progress bars: progress=True   (new Trainer argument)
-------------------------------------------------------
  - An overall bar over the epochs, showing the best valid score so far. It stays when the
    run ends, e.g. at 7/20 after early stopping.
  - A bar for each epoch's training batches and one for validation; both disappear when done.
  - The per-epoch lines and the Outputs/Monitoring lines are printed with tqdm.write(), so
    they appear above the bars and remain as a record afterwards.
  - The batch bar shows the running loss, refreshed every 25 batches (class attribute
    Trainer._postfix_every). Reading the loss makes the cpu wait for the gpu -- the per-batch
    sync the harness otherwise avoids -- so it is not done every batch, and not at all
    when the bars are off.
  - tqdm.auto: widget bars in Jupyter (needs ipywidgets), text bars in a terminal.
  - Off when verbose=False. Can be changed later: trainer.progress.
  - If tqdm isn't installed the harness still works, without bars (_NoBar stands in).
  - Re-running the section 5 benchmark with bars on gave the same times.

5. Speed check: harness vs the notebook train() loop
----------------------------------------------------
Question: is the harness much slower than the plain loop in ageron/Ch14.ipynb? No.
Benchmark (2-layer GRU, vocab 2000, 4096 sequences, batch 32, NAdam, mps, warm-up epoch first):

    Loop                                  Time per epoch (train + valid)
    notebook train()/evaluate_tm()        3.90 s
    harness, defaults                     4.54 s
    harness, amp=False                    3.45 s

  - The harness's extra Python per batch costs microseconds; with amp=False it beats the
    notebook loop, which calls loss.item() (a cpu-gpu sync) every batch.
  - The default fp16 autocast + GradScaler costs ~30% on mps for this model. On a Mac with
    small models, try amp=False (Part 1, section 4.1 already suggests timing both).
  - The "orders of magnitude faster" impression came from Ch14 cell 119: that run's loss was
    stuck at 9.2211 with accuracy 0.0000, on the same nmt_model/optimizer the harness had
    just trained at lr=0.01, so it was not a fair comparison.
